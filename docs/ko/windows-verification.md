# Windows 검증·테스트 절차

**한국어** | [English](../en/windows-verification.md)

이 문서는 **Windows 실기 환경에서 mtw 를 검증하는 절차**입니다. 각 항목은 무엇을 하고, 무엇을 기대하며, 무엇으로 통과/실패를 가르는지를 이 문서 안에 전부 적어 두었습니다. 다른 문서를 찾아보지 않아도 이 문서만으로 검증을 완료할 수 있습니다.

관련 문서: [README](../../README.md) · [psmux 설치](install-psmux.md) · [설정 파일](configuration.md) · [문제 해결](troubleshooting.md)

## 0. 먼저 읽어 주세요 — 검증 범위는 생각보다 좁습니다

**"Windows 판을 처음부터 전부 검증해야 하는가?" — 아닙니다.**

Windows 판(`windows/src/mtw.ps1` · `windows/install.ps1` · `windows/uninstall.ps1`)은 개발 환경인 macOS 에 설치한 PowerShell 7 로 이미 광범위하게 검증되었습니다. 구문 검사, 아래 시나리오 목록의 실기 실행, macOS 판과의 메시지·종료 코드 **바이트 단위 대조**, 실패 주입(백업·복사·삭제·쓰기 실패)까지 수행했습니다. 즉 **"PowerShell 언어 수준에서 명세대로 동작한다"** 는 이미 확인된 상태입니다.

남아 있는 것은 **PowerShell 이 아니라 Windows 라는 OS·콘솔·psmux 바이너리에서만 확인할 수 있는 항목**입니다. 그것이 아래 6가지(W1~W6)이며, 그중 W1·W2 는 **설계 전제 자체**를 확인하는 항목이라 다른 무엇보다 먼저 확인해야 합니다.

전체 시나리오 목록(3장)은 회귀 확인용으로 함께 제공하지만, **우선순위는 1장 → 2장 → 3장** 입니다.

> ### ⚠ 시작하기 전에 백업하세요
>
> **2장부터는 실제 데이터를 건드립니다.** 2장(W4·W5·W6)과 3장 대부분은 `mtw_*` 명령을 **지금 쓰고 있는 세션에서** 실행하므로 실제 `~\.mtw\` 를 그대로 씁니다. `$HOME` 은 세션이 시작될 때 값이 정해지는 읽기 전용 변수라, 3.0 의 격리(`$env:USERPROFILE` 설정)는 **자식 프로세스로 실행되는 설치·제거 스크립트에만** 걸립니다.
>
> 특히 W5 는 목록 파일을 **덮어쓰고**, 시나리오 34 는 `~\.mtw` 를 **통째로 지웁니다.** 시작 전에 세 가지를 백업하세요.
>
> ```powershell
> Copy-Item "$HOME\.mtw\projects" "$HOME\.mtw\projects.verify-backup" -ErrorAction SilentlyContinue
> Copy-Item "$HOME\.mtw\mtw.ps1"  "$HOME\.mtw\mtw.ps1.verify-backup"  -ErrorAction SilentlyContinue
> Copy-Item $PROFILE "$PROFILE.verify-backup" -ErrorAction SilentlyContinue
> ```
>
> 검증이 끝나면 백업을 되돌리거나 설치 스크립트를 다시 실행해 원래 상태로 복구합니다.

## 1. 최우선 전제 확인 (다른 것보다 먼저)

아래 세 항목은 개별 기능이 아니라 **"양쪽 OS 에서 `tmux` 명령 하나로 통일한다"** 는 설계 전제 자체를 검증합니다. 1·2 가 실패하면 개별 시나리오를 아무리 통과시켜도 의미가 없고, **Windows 전용 대체 호출 형태를 추가하는 후속 설계가 필요**합니다. 실패 시 반드시 이슈로 보고해 주세요.

### 전제 1 — psmux 가 `new-session` 의 `-A` / `-c` 플래그를 지원하는가

```powershell
mkdir $env:TEMP\mtw-precheck -Force | Out-Null
tmux new-session -A -s mtwtest -c $env:TEMP\mtw-precheck pwsh
```

| 기대 결과 | 세션 `mtwtest` 가 만들어지고, 그 안의 시작 디렉터리가 `$env:TEMP\mtw-precheck` 이며, `pwsh` 가 실행되어 있다 |
|---|---|
| **판정 기준** | 세션 안에서 `Get-Location` 이 `...\mtw-precheck` 를 출력하면 통과. 오류로 종료하거나 플래그를 인식하지 못하면 실패 |
| **실패 시 무너지는 것** | 세션 생성·경로 지정 명령 자체가 Windows 에서 동작하지 않는다. `mtw_claude` · `mtw_codex` 가 전부 무효가 되며, "양 OS 동일 명령" 전제가 깨진다 |

확인 후 세션을 정리합니다 — `tmux kill-session -t mtwtest`.

### 전제 2 — psmux 세션 내부에서 환경변수 `TMUX` 가 설정되는가

세션 안에서 실행합니다.

```powershell
$env:TMUX
```

| 기대 결과 | 비어 있지 않은 값(소켓 경로 등)이 출력된다 |
|---|---|
| **판정 기준** | 값이 출력되면 통과. 아무것도 출력되지 않으면(빈 값) 실패 |
| **실패 시 무너지는 것** | "세션 내부이면 새 세션 대신 새 창을 만든다" 는 분기가 **항상 거짓**이 되어, 세션 안에서 또 세션을 만들려고 한다. 같은 프로젝트에서 두 에이전트를 함께 쓰는 사용법이 성립하지 않는다. 대체 판별 수단(psmux 고유 환경변수 등)을 찾는 후속 설계가 필요하다 |

### 전제 3 — psmux 가 설치하는 `tmux` 명령이 본체와 동등한가

```powershell
tmux -V
psmux -V
Get-Command tmux | Select-Object Source
```

| 기대 결과 | `tmux -V` 와 `psmux -V` 의 버전이 같고, `tmux` 의 실행 파일이 psmux 설치 경로 아래에 있다 |
|---|---|
| **판정 기준** | 두 버전이 같으면 통과. 다르면 **기록만 남기고** 전제 1·2 의 결과로 판단한다(별도 tmux 가 설치돼 있을 수 있음) |

## 2. Windows 실기에서만 확인할 수 있는 항목 (W1~W6)

0장에서 말한 "본질적 미보증 영역" 입니다. 이 6가지가 전부입니다.

### W1 — psmux 의 `new-session -A` / `-c` 지원 여부

1장 전제 1 과 동일합니다. psmux 바이너리가 Windows 에만 존재해 개발 환경에서 재현할 수 없었습니다. **판정은 전제 1 의 결과를 그대로 씁니다.**

### W2 — psmux 세션 내부의 `TMUX` 환경변수 설정 여부

1장 전제 2 와 동일합니다. **판정은 전제 2 의 결과를 그대로 씁니다.**

### W3 — 오류 메시지의 한글이 Windows 콘솔에서 깨지지 않는가

오류 메시지는 `$host.UI.WriteErrorLine` 으로 출력합니다. macOS 터미널은 항상 UTF-8 이라 코드 페이지 문제가 발생하지 않지만, Windows 콘솔은 코드 페이지의 영향을 받을 수 있습니다.

```powershell
mtw_new                        # 이름 누락 → 오류 두 줄
mtw_rm 없는이름                # 등록되지 않은 이름 → 오류 한 줄
chcp                           # 현재 코드 페이지 확인 (참고용)
```

| 기대 결과 | 아래 문구가 **한 글자도 깨지지 않고** 출력된다 |
|---|---|
| | `오류: 이름을 입력하세요.` / `사용법: mtw_new <이름>` / `오류: 등록되지 않은 이름입니다: 없는이름` |
| **판정 기준** | 물음표·네모·모지바케 없이 그대로 보이면 통과. 깨지면 실패이며, 그때의 코드 페이지(`chcp` 출력)와 콘솔 종류(Windows Terminal / 레거시 콘솔 / VS Code 터미널)를 함께 기록한다 |

Windows Terminal 과 레거시 콘솔 호스트(`conhost`) 양쪽에서 확인해 주세요. 결과가 다르면 둘 다 기록합니다.

### W4 — 백슬래시가 포함된 경로가 한 글자도 바뀌지 않는가

**Windows 는 경로 구분자 자체가 백슬래시**(`C:\Users\...`)이므로, 등록되는 **모든 경로가 이 항목의 대상**입니다. macOS 에서는 예외적인 경우였지만 Windows 에서는 일상입니다. 절차는 아래 5장의 "백슬래시 리터럴 보존" 에 있습니다.

### W5 — 목록 파일을 다시 쓸 때 줄 내용이 보존되는가

`mtw_rm` 은 목록 파일을 다시 쓰면서 **대상 줄만 빼고 나머지를 보존**해야 합니다. 확인할 것은 **줄 내용·순서·주석·빈 줄**입니다.

> **개행 문자는 통일됩니다 — 알려진 동작이며 결함이 아닙니다.** PowerShell 판의 `mtw_rm` 은 파일을 줄 단위로 읽고 다시 쓰므로, **결과 파일의 개행이 그 OS 의 기본 개행으로 통일**됩니다. macOS 의 PowerShell 에서 CRLF 목록 파일에 `mtw_rm` 을 실행하면 결과가 LF 로 통일되는 것을 실측했고, **Windows 에서는 반대로 LF 파일이 CRLF 로 통일될 것으로 예상**됩니다. macOS 판(zsh)은 원본 개행을 그대로 유지하므로 이 지점은 두 구현이 다릅니다.
>
> 이것을 그대로 두기로 한 이유는 두 가지입니다. (1) 목록 파일은 **OS 별 로컬 데이터**이며 경로 표기가 달라 애초에 OS 간 공유 대상이 아닙니다. (2) 각 OS 안에서는 자기 일관적입니다 — 설치 스크립트도 `mtw_new` 도 그 OS 의 기본 개행으로 쓰고, 양쪽 구현 모두 LF·CRLF 어느 쪽이든 읽습니다. 잃는 것은 개행 바이트뿐이고 줄 내용은 보존됩니다.
>
> **따라서 결과 파일에 CR 이 생기거나 사라지는 것만으로는 실패가 아닙니다.** 줄이 사라지거나, 순서가 바뀌거나, 주석·빈 줄이 없어지거나, 줄 내용의 문자가 변형되면 실패입니다.

```powershell
# 목록 파일을 덮어쓰므로 먼저 백업한다 (0장에서 이미 했다면 생략)
$p = "$HOME\.mtw\projects"
Copy-Item $p "$p.verify-backup" -ErrorAction SilentlyContinue

# LF 만 사용하는 목록 파일을 만든다
[System.IO.File]::WriteAllText($p, "# 주석`nalpha=C:\tmp\alpha`nbeta=C:\tmp\beta`n")
(Get-Item $p).Length                     # 기록해 둔다

. $PROFILE                               # 다시 읽기
mtw_rm beta

# 결과의 바이트를 직접 확인
[System.IO.File]::ReadAllBytes($p) | ForEach-Object { $_ }
```

| 기대 결과 | 남은 줄이 `# 주석` 과 `alpha=C:\tmp\alpha` 두 줄이고, 그 순서와 문자가 그대로다 |
|---|---|
| **판정 기준** | 두 줄의 **내용·순서**가 보존되고 `beta` 줄만 사라졌으면 통과. 개행이 `13 10`(CRLF) 쌍으로 바뀌는 것은 **위 상자의 알려진 동작이므로 실패가 아니다.** 줄이 더 사라지거나 문자가 변형되었으면 실패 |

**프로필 쪽도 함께 확인하세요.** 설치 → 제거 왕복 후 프로필이 **바이트 동일**해야 합니다.

```powershell
$b = (Get-FileHash $PROFILE -Algorithm MD5).Hash
pwsh -NoProfile -File .\windows\install.ps1   | Out-Null
pwsh -NoProfile -File .\windows\uninstall.ps1 | Out-Null
(Get-FileHash $PROFILE -Algorithm MD5).Hash -eq $b     # True 여야 한다
```

원본이 CRLF 인 목록 파일로도 같은 절차를 반복해, **줄 내용이 보존되는지**를 확인하세요. 개행이 어느 쪽으로 통일되든 판정에는 영향이 없습니다. 확인 결과에는 **실제로 어느 개행이 되었는지**를 함께 기록해 주세요 — Windows 실기에서 처음 관찰되는 값입니다.

### W6 — 정렬과 탭 완성이 실제 콘솔에서 기대대로인가

**정렬** — `mtw_list` 는 이름 오름차순으로 출력합니다. 정렬이 시스템 로케일에 좌우되면 터키어 로캘에서 `I`/`i` 순서가 달라지는 등의 차이가 생깁니다.

```powershell
# 대소문자가 섞인 이름 여러 개를 등록한 상태에서
mtw_list
```

| 판정 기준 | 출력 순서가 실행할 때마다 동일하고, 사용 중인 로캘을 함께 기록한다. 로캘을 바꿔 실행할 수 있다면 순서가 달라지는지도 기록한다 |
|---|---|

**탭 완성** — 실제 콘솔(PSReadLine)에서만 관찰할 수 있습니다.

```powershell
mtw_rm <Tab>
mtw_claude <Tab>
mtw_cd_<Tab>
```

| 판정 기준 | 앞의 둘은 등록된 프로젝트 이름을 제안하고, 마지막은 `mtw_cd_*` 함수 이름을 제안하면 통과 |
|---|---|

## 3. 시나리오 목록

### 3.0 검증 환경 준비 — 실제 `HOME` 오염을 피하려면

설치·제거 시나리오(1~4, 29~31)는 **프로필과 `~/.mtw/` 를 실제로 수정**합니다. 임시 디렉터리로 격리해 실행하기를 권합니다.

```powershell
$iso = Join-Path $env:TEMP 'mtw-verify'
New-Item -ItemType Directory -Path $iso -Force | Out-Null
$env:USERPROFILE = $iso

# 격리가 실제로 걸렸는지 자식 프로세스에서 먼저 확인한다
pwsh -NoProfile -Command '$HOME; $PROFILE'
```

> **반드시 확인하세요.** 위 출력의 `$HOME` 과 `$PROFILE` 이 **둘 다** 임시 디렉터리 아래를 가리켜야 격리가 성립합니다. Windows 의 문서 폴더 위치는 레지스트리에서 결정되고 OneDrive 로 리디렉션되는 경우도 많아, `$HOME` 만 바뀌고 `$PROFILE` 은 **실제 문서 폴더를 그대로 가리킬 수 있습니다.**
>
> `$PROFILE` 이 임시 디렉터리 밖을 가리킨다면 격리를 포기하고, 대신 **실제 프로필을 먼저 백업**한 뒤 진행하세요.
>
> ```powershell
> Copy-Item $PROFILE "$PROFILE.manual-backup" -ErrorAction SilentlyContinue
> ```
>
> 설치·제거 스크립트도 프로필 수정 전에 자체 백업(`*.bak-YYYYMMDD-HHMMSS`)을 만들지만, 검증 중에는 수동 백업을 하나 더 두는 편이 안전합니다.

**이 격리는 자식 프로세스에만 적용됩니다.** `$HOME` 은 세션 시작 시점에 정해지는 읽기 전용 변수라, 위처럼 `$env:USERPROFILE` 을 바꿔도 **현재 세션의 `$HOME` 은 그대로**입니다. 격리된 환경에서 기능 시나리오까지 수행하려면 **환경변수를 설정한 뒤 새 `pwsh` 세션을 띄우고**, 그 세션에서 설치·`. $PROFILE`·`mtw_*` 를 실행하세요.

```powershell
$env:USERPROFILE = $iso
pwsh                      # 이 자식 세션의 $HOME 이 $iso 다 — 이후 시나리오는 여기서
```

기능 시나리오(5~28, 32~35, 38~40)는 프로필을 건드리지 않지만 **`~/.mtw/` 전체**를 다룹니다 — 목록 파일뿐 아니라 **설치 본체(`mtw.ps1`)를 편집**하고(#27·#33 과 3.2 말미의 dummy 안내), **디렉터리를 통째로 삭제**합니다(#34). 격리 없이 진행한다면 0장의 백업 세 가지를 반드시 먼저 해 두세요.

### 3.1 설치 / 제거 (1~4, 29~31)

| # | 시나리오 | 기대 결과 | 판정 기준 |
|---|---|---|---|
| 1 | 클린 환경에서 `pwsh -NoProfile -File .\windows\install.ps1` 실행 | `~\.mtw\` 생성, `mtw.ps1` 복사, `projects` 빈 파일 생성, 프로필에 로더 블록 1회 추가 | `~\.mtw\mtw.ps1` 존재, `(Get-Item ~\.mtw\projects).Length` 가 **0**, 프로필에서 `# >>> mtw (mw-terminal-worknav) >>>` 가 **정확히 1회**, 종료 코드 0 |

### 3.4 보안 · 복구 (32~35) — 최우선 확인 대상

목록 파일의 내용이 **코드로 실행되지 않는지** 확인하는 항목입니다. 개발 과정에서 실제로 발생했던 결함 유형이므로 가장 먼저 확인해 주세요.

| # | 시나리오 | 기대 결과 | 판정 기준 |
|---|---|---|---|
| 32 | 목록 파일에 형식 위반 줄을 넣고 다시 읽기 | 그 줄만 **조용히 무시**, 코드 미실행, 같은 파일의 정상 항목은 정상 적재 | 아무 메시지도 출력되지 않고, `mtw_list` 에 그 줄이 없으며, 아래 마커 파일이 **생기지 않음**. 정상 항목은 그대로 보임 |
| 33 | 레지스트리에 예약어 키(`rm`) 추가 후 다시 읽기 | stderr 경고, 해당 키의 함수 **생성 건너뜀** | `mtw: 경고: 에이전트 키 'rm' 는 예약어(list new rm help cd) 와 겹쳐 건너뜁니다.` 가 출력되고, `Get-Command mtw_rm` 이 **원래의 고정 명령**을 반환하며(덮어써지지 않음), `mtw_help` 출력과 자동완성 대상에도 나타나지 않음 |
| 34 | `~\.mtw` 를 통째로 지운 뒤 `mtw_new <이름>` | 디렉터리·목록 파일을 만든 뒤 정상 등록 | `~\.mtw\projects` 가 새로 생기고 등록 성공 메시지가 나오며, 즉시 `mtw_cd_<이름>` 사용 가능 |
| 35 | NUL 바이트를 넣은 우회 변형 — (a) 목록 파일에 직접 넣기 (b) `mtw_new` 에 NUL 포함 이름 전달 | (a) 줄 조용히 무시 + 마커 파일 미생성 (b) 형식 위반으로 거부 + 목록 파일 미변경 | 아래 절차의 판정 기준 참조 |

**32번 입력 만들기**

```powershell
$p = "$HOME\.mtw\projects"
Add-Content -LiteralPath $p -Value 'x() { : } ; echo "INJECTED-CODE-RAN" ; f=/tmp/y'
Add-Content -LiteralPath $p -Value '}; New-Item -ItemType File -Path "$env:TEMP\MTW_PWNED"; function _z {'
Remove-Item "$env:TEMP\MTW_PWNED" -ErrorAction SilentlyContinue   # 실행 전 없음을 보장
. $PROFILE
```

판정: 출력에 `INJECTED-CODE-RAN` 이 없고, `Test-Path "$env:TEMP\MTW_PWNED"` 가 **False** 이며, 두 줄 모두 `mtw_list` 에 나타나지 않으면 통과.

**35번 (a) 입력 만들기**

```powershell
$p = "$HOME\.mtw\projects"
$nul = [char]0
$payload = "x$nul}; New-Item -ItemType File -Path `"`$env:TEMP\MTW_NUL_PWNED`"; function _z {"
[System.IO.File]::AppendAllText($p, $payload + "`n")
Remove-Item "$env:TEMP\MTW_NUL_PWNED" -ErrorAction SilentlyContinue
. $PROFILE
```

판정: `Test-Path "$env:TEMP\MTW_NUL_PWNED"` 가 **False**, 해당 줄이 `mtw_list` 에 없음, 같은 파일의 정상 항목은 그대로 적재됨.

**35번 (b) 입력 만들기**

```powershell
$nul = [char]0
$before = [System.IO.File]::ReadAllBytes("$HOME\.mtw\projects")
mtw_new "x$nul}; New-Item -ItemType File -Path `"`$env:TEMP\MTW_NUL_PWNED`"; function _z {"
$after = [System.IO.File]::ReadAllBytes("$HOME\.mtw\projects")
$LASTEXITCODE
Compare-Object $before $after
```

판정: 형식 위반 오류가 나오고 `$LASTEXITCODE` 가 **1**, `Compare-Object` 결과가 **비어 있음**(목록 파일 미변경), 마커 파일 미생성.

확인이 끝나면 넣어 둔 줄을 목록 파일에서 지우세요.

> **시나리오 34 뒤에는 설치 본체를 복구하세요.** `mtw_new` 는 디렉터리와 목록 파일만 다시 만들 뿐 **`mtw.ps1` 은 복원하지 않습니다.** 그대로 두면 다음 세션부터 로더 블록이 조용히 아무것도 읽지 않아 이후 시나리오가 전부 "명령 미인식" 으로 실패합니다. 설치 스크립트를 다시 실행하거나 백업을 되돌리세요.
>
> ```powershell
> pwsh -NoProfile -File .\windows\install.ps1
> ```

### 3.5 중복 키 처리 (39, 40)

목록 파일을 손으로 편집했을 때의 동작입니다. **두 항목은 서로를 가리므로 반드시 둘 다 확인**하세요 — 40번만 보면 39번의 회귀를 놓칩니다.

| # | 시나리오 | 기대 결과 | 판정 기준 |
|---|---|---|---|
| 39 | 목록 파일에 `myApp=C:\path\ONE` / `other=C:\path\o` / `myApp=C:\path\TWO` 세 줄을 넣고 다시 읽기 | **나중 값이 이긴다** | `mtw_list` 에 `myApp` 이 **한 행**만 나오고 경로가 `C:\path\TWO`. `mtw_cd_myApp` 이 `C:\path\TWO` 로 이동. `other` 는 정상 적재 |
| 40 | 목록 파일에 `Foo=C:\path\first` / `foo=C:\path\second` 두 줄을 넣고 다시 읽기 | **먼저 나온 줄이 이긴다** | `mtw_list` 에 **한 행**만 나오고 그 값이 `C:\path\first`. 생성된 이동 함수도 `mtw_cd_Foo` 하나뿐이며 `C:\path\first` 로 이동. `foo` 줄은 아무 메시지 없이 무시 |

40번이 선착순인 이유는 **PowerShell 함수 이름이 대소문자를 구분하지 않아** `mtw_cd_Foo` 와 `mtw_cd_foo` 를 동시에 가질 수 없기 때문입니다. macOS 판도 같은 규칙을 따르도록 맞춰져 있습니다.

### 알려진 차이 3건 — 조치 불요

아래 세 항목은 **원인과 범위가 확정된 차이**입니다. 발견하더라도 결함으로 보고하지 마세요.

**차이 1 — PowerShell 판의 오류 출력은 `2>$null` 로 억제되지 않고 `2>&1` 로 캡처되지 않습니다.**

오류 출력에 `$host.UI.WriteErrorLine` 을 쓰기 때문입니다. **바이트 동일한 메시지와 리다이렉트 가능을 동시에 만족하는 수단이 PowerShell 에 없습니다** — `Write-Error` 는 `$ErrorView` 를 무엇으로 두어도 함수명·파일·줄번호·`Line |` 블록·ANSI 색상이 덧붙고, 커스텀 `ErrorRecord` + `ErrorDetails` + `$PSCmdlet.WriteError` 조합도 똑같이 장식됩니다. 이 도구가 요구하는 것은 **메시지 문구가 macOS 와 같을 것**이므로, 문구를 택하고 리다이렉트를 포기했습니다.

- **보장되는 것**: 오류 문구와 종료 코드가 macOS 와 동일하다.
- **보장되지 않는 것**: `mtw_rm foo 2>$null` 로 오류를 숨기는 것.

**차이 2 — `&&` / `||` 연쇄가 macOS 와 다르게 동작합니다.**

PowerShell 의 `&&` / `||` 는 `$LASTEXITCODE` 가 아니라 `$?` 를 보는데, **함수의 비종료 오류는 `$?` 를 뒤집지 않습니다**(`Write-Error` 를 어느 위치에 두어도 `$? = True` 로 관측됨 — 네 가지 배치로 실측). `$?` 를 뒤집을 수 있는 것은 `throw` 뿐이지만 제어 흐름과 출력 형식이 달라집니다. 따라서 실패 시 **`$LASTEXITCODE` 를 1 로 설정하는 것이 가능한 최선의 근사**입니다.

- **보장되는 것**: `$LASTEXITCODE` 로 성공/실패를 판정할 수 있다.
- **보장되지 않는 것**: `mtw_rm foo && echo ok` 형태의 연쇄 제어.

```powershell
mtw_rm foo
if ($LASTEXITCODE -eq 0) { 'ok' } else { 'failed' }
```

**차이 3 — `mtw_rm` 이 목록 파일을 다시 쓸 때 개행이 그 OS 의 기본 개행으로 통일됩니다.**

macOS 판(zsh)은 원본 개행을 그대로 유지하지만, PowerShell 판은 파일을 줄 단위로 읽고 다시 쓰기 때문에 결과 파일의 개행이 통일됩니다(macOS 의 PowerShell 에서 CRLF → LF 로 통일되는 것을 실측). 목록 파일은 경로 표기가 달라 **OS 간 공유 대상이 아니고**, 각 OS 안에서는 자기 일관적이며(설치 스크립트도 `mtw_new` 도 그 OS 기본 개행으로 씁니다), 양쪽 구현 모두 LF·CRLF 어느 쪽이든 읽으므로 그대로 두었습니다.

- **보장되는 것**: 대상 줄만 제거되고 나머지 줄의 **내용·순서·주석·빈 줄**이 보존된다.
- **보장되지 않는 것**: 원본 개행 문자의 유지.

**목록 파일을 읽을 때는 양쪽이 동일합니다.** CRLF 목록 파일에서 줄 끝의 CR 은 **양 OS 모두 경로 값에서 제거**되므로, 등록된 경로와 `mtw_cd_*` 의 이동 대상이 같습니다.

**프로필(`$PROFILE`)은 이 제약을 받지 않습니다.** 설치·제거 스크립트는 프로필을 **바이트 단위로 읽고 씁니다** — UTF-8 BOM · CP949 · latin-1 등 어떤 인코딩이든 왕복 후 바이트가 그대로이고, 개행도 원본을 유지합니다. 추가되는 로더 블록의 개행도 **프로필이 쓰고 있는 것에 맞춥니다**(CRLF 프로필에는 CRLF). 마커 판정은 줄 끝 CR 을 무시하므로 CRLF 프로필에서도 정상 동작합니다.

### 백슬래시 리터럴 보존 절차 (38 / W4)

**Windows 는 경로 구분자 자체가 백슬래시이므로 등록되는 모든 경로가 대상입니다.** 특수한 경로 하나를 만들어 보는 것으로 끝내지 말고, **평범한 경로의 등록 → 목록 출력 → 해제 전 과정에서 경로가 한 글자도 바뀌지 않는지** 확인하세요. 목록 파일에 잘못 기록되는 것은 표시 오류가 아니라 **데이터 파손**이므로 **파일 내용을 바이트 수준으로** 확인합니다.

```powershell
# 1) 평범한 경로
Set-Location C:\Users\minwoo\projects\myApp
mtw_new myApp

# 2) 기록된 내용을 바이트로 확인
$p = "$HOME\.mtw\projects"
Get-Content -LiteralPath $p -Raw
[System.IO.File]::ReadAllText($p)      # 두 값이 입력한 경로와 정확히 같아야 한다

# 3) 표시 확인
mtw_list                               # 경로가 그대로 보여야 한다

# 4) 이동 확인
mtw_cd_myApp
(Get-Location).Path                    # 등록한 경로와 정확히 같아야 한다

# 5) 해제 메시지 확인
mtw_rm myApp                           # 메시지의 경로가 그대로여야 한다
```

추가로 **탭 문자로 해석될 여지가 있는 경로**도 확인합니다. 예를 들어 `C:\temp\a\tb` 같은 폴더를 만들어 같은 절차를 반복하고, 목록 파일에 **리터럴 `a\tb`** 로 기록되는지(탭 문자로 바뀌지 않는지) 바이트로 확인하세요. 파일에 실제 탭(9)이 들어갔다면 실패입니다.
